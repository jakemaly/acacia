## Applying the design across tasks

Acacia states a verifiable result and the constraints that matter. One foreground action owns that objective until it succeeds or needs a decision. Each action keeps enough state to select equivalent targets, avoid repeatedly trying an unchanged failure, and preserve progress through local recovery. Use shared outcome categories and action-specific facts for the game work.

| Seam | Recommended change |
| --- | --- |
| Model and prompt | Use the fewest decisions that change the outcome. Set a goal such as obtain eight drops, reach a supported position near a landmark, or equip an item set. Give the next model turn on goal completion, a meaningful hazard or constraint, or exhausted progress. Keep objective changes and their evidence in the dashboard. |
| Tool arguments | Make normal calls express desired state and admissible scope. Collection accepts quantity and, when needed, a work area or connected deposit. Navigation accepts a region and safe arrival conditions. Exact positions stay available for work where the individual cell matters. Express mutually exclusive operations in the tool catalogue. |
| Navigation | Rank nearby approaches by reachability, expected damage, footing, and supplies required. Allow bounded digging, scaffolding and local replans inside the original request. Return the best position reached and the remaining blocker when every candidate is exhausted. Keep permanent hazards and material reserves enforced through each replan. |
| Gathering, building and crafting | Evaluate the live inventory deficit and carry capacity. Chain movement, equip, execution and observed pickup through one task. Keep one registry of recipes, ingredient acquisition and equipment slots. Prefer verified item gains or equipped slots to the number of substeps executed. |
| Combat and survival | Rank reachable combat and loot positions within the chosen work area. Read projectile and weapon timing locally. Keep a usable firing or melee position until it stops working, and resume after a local pause when the situation allows. Prefer nearby verified cover to a fixed-distance retreat, with distance as a fallback when the local positions fail. |
| Orchestration | Distinguish traveling, productive work, a finite spawn or cooldown wait, local recovery, a stall, and a terminal result. Use progress appropriate to each phase. Movement can count if it closes distance to an admissible target or validates new terrain. Only new evidence or elapsed budget should turn a stall into a model decision. Retrieve the final result once through Mine AI's existing foreground ownership rules. |
| State and observations | Put the decision-relevant result first. Maintain objective, progress, position, safety and inventory in typed runtime state. Let full maps and logs remain available for drill-down. After compaction or reconnect, reattach the current objective, action handle and a fresh baseline. |
| Testing | Compare tasks from matched starts with the same tools, client and reasoning level. Measure idle ticks separately from response gaps, along with completed objectives, damage, supplies, and recovery distance. Use several layouts and seeds, and include safe return from a hazardous expedition as part of success. |

Alto Clef supplies a reusable pattern for composing verified prerequisites. A task retains its objective and repeatedly selects the first unmet prerequisite from current world state. Defense and food can take priority before the task continues. Borrow that pattern inside Mine AI's existing foreground and reflex ownership. Let a small set of task types share mining, routing, crafting, equipping, and recovery. Equip diamond is one way to test composition across multiple prerequisites. A bounded gathering objective and a reach-region objective independently test whether the same contract works beyond equipment. [Alto Clef task runner](https://github.com/gaucho-matrero/altoclef/blob/af22e3bc2f03dde45da703f5f7535baae18ea486/src/main/java/adris/altoclef/tasksystem/TaskRunner.java#L21-L40) · [Mine AI foreground lifecycle](https://github.com/aibengineering/mine-ai-mcp/blob/de4fef3260424d973bf81d0eaa15ff1a2f73ecff/docs/mcp/async-actions.md)

Start with the same Acacia model and same-world fixtures for gathering and travel. Compare the deployed interface with a candidate that keeps executing while reaching, collecting, or working through a time-bounded local interruption. Measure the Normal and Hardcore policies from matched Nether arrivals, then change reasoning effort separately. Full runs on other seeds check whether the gains transfer.

## First changes

- Separate block lists from portal presets and chest transfers from sorting in the model-visible tool catalogue. These variants call the current Minecraft implementation. Validate transfers by opening a real fixture chest and reading what was deposited.
- Project a compact status from the structured observation. Replay on 96 recorded status results brought the median from 2,096 to 345 estimated tokens and cut total status output by about 84%. Full status remains queryable. Lower the default block search to four hits per block type and keep explicit limits and terrain grids available.
- Use the existing batch tools as the normal entry points. While waiting for a gathering batch, the harness can continue polling within the original time allowance when inventory count is increasing. Stalls, safety interrupts, health loss and tool changes return control to the model. The model still receives verified gains and can select the next objective.
- Resolve OAuth again when Pi supplies a pre-resolved token for compaction. Threshold and overflow regressions exercise the real request preparation with a fixture response. A separate summary request using the live OAuth account succeeded.

## Alto Clef already does “equip diamond”

Alto Clef's `@equip diamond` command expands to diamond helmet, chestplate, leggings and boots. `EquipArmorTask` asks for only pieces neither carried nor worn. It delegates acquisition to `CataloguedResourceTask` and then moves each piece into its corresponding slot. It finishes when the armor is actually equipped. The catalogue defines the armor recipes once and treats diamond as a resource obtained from either normal or deepslate ore. `MineAndCollectTask` delegates to a tool-acquisition task if the pickaxe requirement is unmet. The live tool catalogue has `destroy_end_crystal`, `prepare_dragon_perch`, `attack_dragon_perch`, and `shoot_dragon`. The first handles one crystal. Preparation makes and verifies a low staging approach. The attack waits for and handles one melee window, then goes back to safety on takeoff or returns on a confirmed death or other stop. ## Adaptive reasoning

Acacia configures one medium thinking level, and the dashboard currently reports the constant. Pi supports `session.setThinkingLevel` with a transcript change and event, and the local model configuration maps low, medium and high levels. Keep normal safety limits in the executor. Measure a fixed-low planning baseline alongside an adaptive variant. Use lower effort for routine handoff and known objectives, and spend extra reasoning when selecting an approach, crossing a genuinely new hazard, or resolving a typed blocker after observed lack of progress. Escalate only on a changed decision, and restore low effort once a concrete objective is chosen. Retrying identical validation failures or waiting while a long action is still making progress are cases for deterministic handling. Record requested and effective effort, result-to-next-action latency, physical idle time, outcome and safety so an apparent speedup cannot come from more retreats or more damage.
